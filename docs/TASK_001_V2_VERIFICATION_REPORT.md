## السبب والإصلاح

فحص SQL القديم أثبت عدم تطابق قائمة الأعمدة والقيم في إدخال حركات المخزون: 14 عموداً مقابل 15 قيمة. استبدل مسار التأكيد بإدخالات متوافقة مع المخطط، واختبر على PostgreSQL محلية. هذا عيب مؤكد في الكود؛ لم تفحص سجلات الإنتاج لإثبات أنه السبب الوحيد لكل رسالة خطأ عامة سابقة.

نقل إنشاء المستند وتأكيده وتعديله وإلغائه إلى خدمة مخصصة. التأكيد يستخدم معاملة واحدة وأقفال صفوف، ويعيد التحقق من الشركة والمستودعات والمواقع والكميات وأهلية كل رولة. الفشل يعيد جميع التغييرات، والتأكيد المتكرر لا ينشئ حركات إضافية. مفتاح طلب وبصمة محتوى يمنعان تكرار الإنشاء ويرفضان إعادة استخدام المفتاح بمحتوى مختلف.

تقتصر الأهلية على AVAILABLE ذات طول موجب في المستودع والموقع المصدر المحددين. تمنع الحالات المحجوزة والمباعة والتالفة وAT_EXTERNAL_JOB وبقية الحالات غير المؤهلة. التغيير في الرولة يقتصر على المستودع والموقع ووقت التحديث؛ تبقى الهوية والباركود والأمتار والأوزان والتكلفة والعملة والحالة محفوظة. تسجل حركتا خروج ودخول دون تعديل كمية المخزون الإجمالية أو قيمته أو إنشاء قيود محاسبية.

## الواجهة والحماية

حفظت شاشة المناقلات الحالية والباركود والبحث والفلاتر والترجمة العربية والتركية. أضيف اختيار رولة، عدة خامات، خامة كاملة، وخامة بحسب لون أو عدة ألوان، ضمن مستند واحد وقائمة معرفات فريدة. تحمل جميع الصفحات، وتحترم موقع المصدر، وتتيح إزالة الرولات فردياً ومراجعتها مجمعة بحسب الخامة واللون مع الإجماليات. تغيير المصدر يمسح الاختيار ويلغي أثر الطلبات القديمة.

أضيف مسار أهلية خاص بالمناقلات؛ لم يتغير سلوك API المشترك onlyAvailable. تستخدم صلاحيات inventory.manage أو المدير مع نظام الجلسات وعزل الشركات القائم. ربط النقل المباشر للرولة بالتحقق والمعاملة المشتركة مع إبقاء نقل الموقع داخل المستودع. رسائل عربية مفهومة وتسجيل تقني محدود دون أجسام الطلبات أو أسرار الاتصال.
